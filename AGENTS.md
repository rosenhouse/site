## Scope

Do not file issues or PRs against any other repos.


## Planning

Keep design notes, plans, requirements and open questions in GitHub issues,
not in repo files.


## Attribution of GitHub posts

Anything posted to GitHub from an AI agent session appears under the repository
owner's account. Every issue, issue comment, pull request description,
review, and review comment that an AI agent writes must begin with the line

    🤖 Created by AI (Claude) 🤖

(or other agent name in parens) as its first line, before any other text.
This applies without exception.


## Testing

Except when doing prototyping and research, default to red/green TDD for most work:
write a failing test first, then the minimum code to make it pass, and after a few
rounds of that, refactor!

If I were to mutate or remove the production code, then a test ought to fail.


## Web dev
For web development, follow the [guidance here](https://github.com/GoogleChrome/modern-web-guidance).


## Writing style

This applies to code comments, commit messages, issues, markdown docs, etc.
- Write as little as possible.  Clean code and tests should be largely self-documenting through variable and function names.
  Aggressively remove prose that doesn't add significant value beyond the code itself.
- Prune historical context that isn't immediately necessary to understand current behavior.
- Prefer short, complete sentences with a clear subject and verb.  A noun phrase is not a sentence.
- Use idiomatic conversational English.
  - Awkward: CI runs no linter.
  - Better: CI does not run a linter.
- When writing a proposal or change summary, lead with a clear goal.  For example, in a PR description that introduces a linter:
  - Best (clear goal): CI should run a linter.


## Adversarial review

For any nontrivial work, before claiming to be done, spawn at least one
subagent to do an "adversarial review" and address its findings.

Here are some possible reviewer personas to use, depending on context:
- An exploratory tester, who tries to use the software (not just reading code) and looks for surprising behavior
- A senior engineer who will be maintaining the code going forward.  They value clean, self-documenting code and meaningful tests.
  They also demand clear, minimal prose and enforce the writing style rules above.
- A domain expert, who is looking for correct information presented clearly.
